3. AUDIT TAXONOMY
-----------------

Only these statuses are used for clinical-source classification:

  EXACT_SOURCE
    The relevant stored text matches the source text for the cited task.

  FAITHFUL_STRUCTURED
    A data structure preserves the required source action without material
    semantic loss, although it is not a verbatim prompt.

  ACCEPTABLE_EDITABLE_VARIANT
    A source-anchored shorter or editable wording retains the required action,
    but still needs clinician confirmation before being treated as final.

  PARAPHRASED_REVIEW_REQUIRED
    A source idea is restated, but wording or omitted conditions make clinical
    review necessary.

  SYNTHETIC_PLACEHOLDER
    The stored content is generated/demo wording rather than source content.

  MISSING
    A source-required prompt, rule, field, branch, output, or provenance is
    not represented in the examined implementation.

  MISPLACED
    A source-relevant action appears at the wrong session, stage, role, or
    order.

  CONTRADICTS_SOURCE
    The current behavior or wording conflicts with an explicit source rule.

The status on a session row is the highest-risk finding for that session. It
does not erase lower-risk EXACT_SOURCE items listed later.

5. DATA-PLACEMENT AND EXECUTION DISTINCTION
--------------------------------------------

Catalog / Builder path
  sessionOutlines + promptBlueprints in session-catalog.ts
    -> createSessionSeeds()
    -> localStorage-backed catalog
    -> getSessionNodes() / getSessionPrompts()
    -> ProtocolPage Session Explorer, canvas, and Node Inspector

Protocol graph / release path
  protocolGraphNodes and protocolGraphEdges in Dexie
    -> getProtocolGraph()
    -> immutable release snapshot
    -> runtime session entry/completion and edge traversal

Runtime message path
  release snapshot current node
    -> getSessionPrompts(sessionDefinitionId, node.id)
    -> provider request if a catalog PromptItem matches
    -> otherwise node runtimeAction payload text or node content

These are separate sources. A catalog PromptItem visible in the Builder is not
automatically a release-graph node, and a release-graph node is not guaranteed
to have a matching catalog PromptItem. Accordingly, a UI display, a graph
shape, or a runnable node is not proof that the delivered content is sourced.

Specific current paths:

1. The Builder canvas is rendered from sessionFlowNodes, which is built from
   getSessionNodes(selectedSessionMeta.id), not graphQuery.data.nodes. The
   right-side prompt list uses getSessionPrompts(selectedSessionMeta.id,
   selectedSessionNode.id). The graph query is a separate data source.

2. The built-in release generator in protocol-api.ts reads only
   getProtocolGraph(protocolId, "SESSION-03"). It does not create an S01-S08
   release from the catalog.

3. The built-in Dexie v3 seed creates REL-DEMO-1 with eight generic nodes named
   RT-NODE-* under protocol ID TBCT-BR-001 and session ID SESSION-03. Its
   content includes a generic check-in, activity, homework, and safety branch;
   it is not any source Session 03 Intra-TR sequence.

4. The special real-S03 importer uses protocol ID tbct-br-001 and session ID
   tbct-br-001-session-03. getProtocolGraphApi() invokes it only when both
   lower-case/long identifiers are passed. The main Builder calls the graph API
   with TBCT-BR-001 and catalog IDs such as tbct-session-03, so this special
   import condition does not match that route.

5. For a legacy REL-DEMO-1 node, getSessionPrompts("SESSION-03", "RT-NODE-*")
   normalizes only the session ID to tbct-session-03. The catalog's S03 nodes
   are named q1_situation, q2a_automatic_thought, etc., not RT-NODE-*. No
   PromptItem therefore matches the release node ID. The deterministic provider
   falls back to the legacy release node's generic content.

6. The static S03 graph itself has a transition from mandatory_safety_check
   conditioned on safetyClear == true, but its runtime action writes safetyCheck.
   runtime-context.ts does not derive safetyClear. Static inspection therefore
   finds no matching transition field for that edge. This is an execution-path
   observation, not a claim that the S03 clinical source has been executed.

8. SESSION COMMON RULES ROOT-CAUSE ANALYSIS
-------------------------------------------

Root cause 1: defaultSessionCommonRules contains an entry only for
tbct-session-03. No default SessionCommonRules record exists for S01, S02, or
S04-S08.

Root cause 2: getSessionCommonRules() returns null when that session has no
default record. ProtocolPage renders empty controlled fields in that case, and
all onChange handlers are guarded by `sessionCommonRules && ...`. The fields
therefore appear as "Session Common Rules" but cannot acquire rules for those
sessions through that view.

Root cause 3: readStore() ignores persisted common-rule records that do not
have a corresponding default record. This prevents a durable catalog rule set
from being reconstructed for S01, S02, or S04-S08 through the current merge.

Root cause 4: even the S03 common rules are UI/catalog metadata only. The
runtime node executor sends editableText, aiInstruction, fields, validation,
and node safety IDs to the provider. It does not load or inject
SessionCommonRules. Session-wide restrictions therefore do not control runtime
delivery.

10. SOURCE-TRACE AND GROUPING FINDINGS
---------------------------------------

1. Every catalog PromptItem carries only a broad session-level source trace.
   It has no source line range, exact-source hash, source block ID, or source
   excerpt. The presence of `verbatimText` therefore does not establish that the
   text was imported verbatim.

2. sessionOutlines controls stage grouping for seven sessions. Its stage titles
   and clinicalPurpose strings are author-created summaries, not source sections
   with a one-to-one trace. `requiredFields`, `completionRule`, `branchRules`,
   and `restrictions` do not encode most source conditions.

3. The legacy tbct-session-03 outline and promptBlueprints entries remain in
   session-catalog.ts, but createSessionSeeds() bypasses them and instead maps
   REAL_SESSION_03_NODES. This stale parallel S03 content is not trustworthy as
   current clinical source content.

4. PromptItems are editable and persistable. For S01, S02, and S04-S08,
   readStore() accepts persisted node and PromptItem values after the first
   catalog initialization. This makes current browser content potentially differ
   from the static seed without source provenance.

5. Session Definition status values such as draft, reviewed, or ready are
   implementation metadata. They do not demonstrate clinician approval of any
   source section.
